# MemoPal 伙伴养成与搭配体验计划

状态：分阶段实施中。阶段 A 的服务端关系状态与伙伴空间、阶段 B 的首位伙伴样板正在验收；阶段 C 尚未完成。本文以现有移动端伙伴衣橱、Appearance Studio、等级和练习记录为起点。

## 1. 想让用户感受到什么

伙伴会陪着我学习，记得我们一起完成的事；我可以和它短暂互动，并把它打扮成自己喜欢的样子。用户打开页面后的第一眼应看到伙伴的状态和动作，而不是一排装备格子。

核心循环：

```text
完成一次真实练习 / 复习
  → 伙伴对这次学习作出一句简短回应和一个动作
  → 关系成长，记录共同里程碑
  → 达到等级 / 里程碑时获得可搭配的物品或动作
  → 回到伙伴空间互动、试穿、保存造型
```

关系成长不改变复习调度或学习成绩。断签、答错、几天未登录不会让伙伴挨饿、生病、退化或责备用户；回来时给予欢迎和轻量的继续入口。

## 2. 当前基础与缺口

| 已有 | 需要补齐 |
| --- | --- |
| 5 个等级解锁伙伴；个人资料可选伙伴或照片 | 伙伴是静态头像，没有可换装的身体、动作或个性回应 |
| `frame / decoration / outfit` 三个外观类别；可预览并保存 | 图层只是叠在头像上，缺少每个伙伴的锚点、遮挡关系和素材校验 |
| Appearance Studio 可配置名称、图片、等级、顺序和启用状态 | 缺少兼容角色、搭配套装、故事文案、动作关联及上传预览校验 |
| 后端记录 XP、等级、连续天数、练习结果 | 没有独立的伙伴关系进度、互动状态和伙伴可见的共同回忆 |

当前 `MemoryAvatar` 仍负责头像和外观叠加；它应继续服务 Profile 的小尺寸展示。完整角色舞台需要独立渲染器和专用素材，不能靠放大现有头像图实现。

## 3. 页面与操作流程

### 伙伴空间：从 Profile 进入的养成主场景

```text
┌──────────────────────────────┐
│ 伙伴名字 · 关系阶段      ⋯    │
│                              │
│       可互动的完整角色        │
│       背景 / 小道具 / 动作     │
│                              │
│ 「今天一起复习了 2 组！」      │
│ [陪我复习] [摸摸它] [换装]     │
│                              │
│ 关系进度 ━━━━━━━  下一段故事  │
│ 最近共同回忆 · 解锁预告        │
└──────────────────────────────┘
```

- 伙伴可点按，有眨眼、转头、挥手等短反馈；文字不挡住角色。
- 主行动“陪我复习”进入现有待复习列表或练习入口，不另造练习系统。
- 完成练习后返回时，展示一个短动作、具体但不泄露答案的反馈，例如“今天一起完成了 2 组复习”。每次会话最多展示一次，避免频繁打断。
- “共同回忆”记录可公开展示的事实：首次完成练习、达到某等级、完成第 10 次复习、获得套装。不得存储原始答案、记忆内容或宫殿照片。
- 当用户选择照片作为 Profile 头像时，伙伴空间仍展示已选伙伴；照片只是个人身份展示，不会替代伙伴本体。

### 伙伴衣橱：一个角色舞台，直接在角色上试穿

```text
┌──────────────────────────────┐
│ 返回       伙伴衣橱      收藏  │
│                              │
│      完整角色实时试穿舞台      │
│   [随机搭配] [恢复已保存]      │
│                              │
│  伙伴  头饰  服装  背饰  手持  │
│  ─────────────────────────   │
│  横向物品卡：图像、名称、状态  │
│  套装提示 / 解锁方式          │
│                              │
│        [保存这套造型]          │
└──────────────────────────────┘
```

- 点击物品立刻更新角色，角色做一次轻量试穿动作；再次点击已选物品可卸下。
- 不可穿戴物品仍可查看获得条件和局部预览；锁定态不能保存。
- “随机搭配”只使用已解锁且兼容当前伙伴的物品，结果先预览，用户确认后保存。
- 可保存少量命名造型，快速切换。退出有未保存修改时给出保留/放弃选择。
- 头像框与个人照片放在“资料外观”入口，和角色穿戴分开。Profile 使用同一份已保存搭配生成小尺寸角色头像；无需每次真的截屏上传，优先复用相同图层合成逻辑。需要分享图或系统头像文件时再导出静态图。
- 画面重心留给角色。卡片以素材和状态为主，描述仅在选中后的详情区出现。

## 4. 养成、互动、收集的规则

### 关系成长

- 关系进度与账号等级区分：账号等级继续决定学习阶段；关系进度表示与当前伙伴一起练习的经历。
- 关系点数只来自服务端已确认的有效练习/复习，以及每日首次轻互动。重复点按、重复提交同一练习、切换伙伴不刷点。
- 切换伙伴时保留每个伙伴自己的关系进度和共同回忆；不惩罚切换。关系阶段初期可定为“初识 → 熟悉 → 默契 → 挚友”，阈值需在小规模测试后调节。
- 每个阶段提供看得见的新反馈：新动作、台词、场景小物或服装；避免只改一根进度条。

### 互动

- 先做三种短互动：点按伙伴的即时动作、每日一次“打招呼”、练习完成后的主动回应。
- 回复从经过审核的中英文文案池选择，按伙伴性格、关系阶段和事件类型变化；初版无需生成式对话。
- 同一动作有冷却和文案去重；弱网下可播放本地动作，但关系奖励以服务端确认为准。
- 支持减少动态效果：改用静态表情和文字提示；屏幕阅读器能读出状态与动作。

### 搭配与收藏

- 初版槽位：头饰、服装、背饰、手持。头像框独立；后续只有在素材和需求证明可行时扩展表情/房间。
- 每件物品显示“已拥有 / 未解锁 / 已穿戴”和清楚的取得方式。解锁条件初版只用等级或指定成就，避免同时出现多种货币。
- 套装由 2–3 件同主题物品组成。集齐并穿戴时有一个短动作与“套装故事”；套装效果是外观与情感反馈，不提供学习数值加成。
- 每个伙伴有兼容清单。没有适配图层的服装不能在该伙伴上显示或出售为可穿戴状态。

## 5. 素材与渲染规范（先解决现在的跑位问题）

- 现有 5 张伙伴图是方形头像插画，不能直接承担全身换装。先为角色确定统一正面/三分之四站姿、画布尺寸、头部与身体锚点；每个伙伴各自导出基础身体、表情与可穿戴图层。
- 所有同一角色的图层使用完全相同的透明画布和坐标原点；首个猫头鹰样板的实际素材尺寸为 1254 × 1254。策划配置的是槽位与兼容关系，必要时才配置小幅锚点校正。禁止在移动端通过百分比缩放和人工平移逐件凑位置。
- 分层顺序示例：背景 → 背饰 → 身体 → 服装 → 手持 → 头饰 → 表情/特效。每个槽位有固定遮挡规则，并提供各伙伴的素材预览合成图。
- Profile 小头像、衣橱舞台和分享图共用同一套造型数据。照片头像框仍走独立的圆形头像合成器；角色服装不叠在用户照片上。
- 素材上传时校验尺寸、透明通道、画布边距、文件体积和兼容角色；后台同时显示角色合成预览与小头像预览。未通过视觉验收的物品不发布。
- 先做一位伙伴的一套完整可穿戴样板，确认站姿、锚点、动作与小头像都正确，再按同规范扩展其余伙伴。已上架伙伴始终保留可用的基础形象。

## 6. 数据与后台设计

| 领域 | 建议职责 |
| --- | --- |
| 伙伴目录 | 角色基础素材、性格文案、动作清单、兼容槽位；后台可启停与排序 |
| 外观目录 | 物品、槽位、对应角色素材、套装、取得条件、预览、发布状态；沿用 Appearance Studio 扩展 |
| 用户伙伴状态 | 每个用户 × 伙伴的关系阶段/点数、首次相遇、最近互动；服务端管理 |
| 已拥有物品与造型 | 解锁记录、当前穿戴、命名造型；服务端校验归属、兼容性与槽位互斥 |
| 共同回忆 | 从已确认学习事件生成有限、无敏感内容的事件摘要，支持去重与分页 |

实施时先复用现有 `AppearanceDefinition`、头像选择与练习记录。只有在做完整角色换装时才添加兼容角色/图层元数据、用户伙伴状态和造型表，并创建新迁移；现有 `SelectedAvatarFrameId` 等字段需要明确迁移/兼容策略。后台解锁条件和关系阈值由服务器判定，客户端只负责展示；提交造型时验证用户、拥有权、角色兼容、槽位互斥和幂等。不要复制一套客户端可自行增长的关系点数。

## 7. 分阶段交付与验收

### 阶段 A：验证伙伴“有回应”

1. 在 Profile 增加伙伴空间入口，使用当前伙伴形象和已有学习记录展示今天的共同进展。
2. 实现短互动与练习完成反馈，先用现有静态伙伴图加轻动作与文案。
3. 建立服务端关系进度与事件去重；做首次见面、练习完成、再次回来三条完整路径。

验收：用户完成一次复习后能看到对应伙伴反馈；重复提交不会重复加关系进度；切换账号不会串数据；离开数日回来没有惩罚文案。

### 阶段 B：做出真正的角色换装

1. 制作一位伙伴的完整分层素材样板和 2 套主题物品；形成素材模板与后台预览规范。
2. 衣橱改为完整角色舞台、横向物品栏、试穿反馈、保存/撤销/随机搭配。
3. 后端增加兼容性、拥有权和造型保存契约；Profile 小头像复用已保存造型。

验收：同一套造型在舞台和 Profile 中一致；换装不遮挡眼睛/手部且不同设备尺寸不跑位；锁定或不兼容物品不能保存；照片头像不会被服装覆盖。

### 阶段 C：扩大陪伴与收集深度

1. 将规范扩展到其余伙伴，增加各自回应、表情和兼容物品。
2. 上线共同回忆、套装故事、命名造型与收藏视图。
3. 后台支持预览、发布、撤回和调整取得条件；建立内容制作与设备验收清单。

验收：所有可选伙伴都有基础互动和至少一组可穿戴造型；后台新增已审核物品无需发版即可进入目录；撤回物品后已有造型有安全回退，不出现空白角色。

## 8. 体验是否有效的观察指标

- 首次进入伙伴空间后，完成“互动 → 练习 → 返回查看反馈”的比例。
- 衣橱试穿到保存的比例、保存后 7 天再次换装的比例。
- 伙伴页面是否帮助用户更容易进入真实复习；观察复习完成率，而不是只看页面停留时长。
- 反馈是否重复、打断学习或让用户感到压力；通过可用性访谈和反馈入口确认。

如互动率高但复习完成率下降，应缩短动画和台词，并把复习入口放回首要位置。

## 9. 本轮明确的产品决定

- 伙伴是独立角色；用户照片仍是个人资料照片。
- 关系成长来自真实学习和有限互动，不采用饥饿、死亡、惩罚式断签。
- 角色服装与头像框分属不同的渲染场景。
- 首个可交付样板先验证一位角色的完整链路，再扩展目录；不会把现有方形头像图当作可换装身体。

## 10. 当前实现与未完成项（2026-10-17）

- 已实现记忆猫头鹰的全身分层造型舞台、星穹学者与花园漫游者两套头饰/围巾、试穿、随机搭配、撤销与保存。个人照片与头像框保持独立；相同已保存造型用于伙伴空间与 Profile 的角色展示。
- Appearance Studio 可配置兼容伙伴、套装和新槽位；上传的可穿戴 PNG 校验 1254 × 1254 画布与透明像素。上传预览仍只是头像缩略合成，不能代替全身角色的人工视觉验收。

## 11. 关系成长与共同回忆完善计划（产品方案，尚未实施）

### 当前问题

- 关系点数已有服务端计算：一次练习/复习 +5，每日第一次问候 +1；阶段门槛为 25、100、300 点。
- 目前阶段只改变“初识 / 熟悉 / 默契 / 挚友”称号和进度，不会解锁任何实际内容；页面也没有解释点数从哪里来或下阶段会得到什么，所以进度条缺少目标感。
- 共同回忆已记录练习、问候和里程碑事件，但一般练习摘要高度重复；页面接口最多返回 10 条且只取最近一次练习，不能支撑长期回看。最近练习还会在顶部反馈和列表中去重，用户不容易理解两者差异。
- “最近的共同回忆”目前是活动记录列表，不是具有独特内容的回忆故事。空态没有解释之后会出现哪些值得收藏的节点。

### 用户目标与体验原则

1. 用户一眼能知道关系进度代表什么、怎样推进、下一个阶段会得到什么。
2. 真实学习是关系成长的主要来源。问候只提供轻量补充，不让用户感觉必须每日签到或照料宠物。
3. 回忆只记录值得纪念的共同经历，不把每次普通点击都做成通知或重复日志。
4. 页面回看提供情感价值和新发现，而不是靠红点、连续签到压力或无意义的停留时长。
5. 成长奖励以外观与互动为主，不影响学习成绩、复习调度或记忆内容。

### 建议的用户流程

```text
完成真实练习/复习
  → 即时看到伙伴回应与本次关系点数变化
  → 若达成重要节点，生成一条专属共同回忆
  → 伙伴空间显示“新回忆”入口及下一阶段奖励预告
  → 用户点开回忆时间线，查看事件和伙伴反应
  → 下一次练习或阶段变化后再回来查看
```

#### 关系成长区

- 将标题改为“关系成长”，在进度条附近用一句短说明解释规则，例如“每次完成练习 +5；每天首次问候 +1”。
- 清楚呈现当前阶段、当前点数、下一阶段门槛和奖励预览，例如“熟悉 · 32/100 点 · 默契后解锁新的伙伴回应”。不只显示含义不明的“还差 25”。
- 每个阶段至少绑定一个已存在或可配置的可见奖励：伙伴回应/动作、场景装饰、称号或指定外观物品。阶段达成时立即展示奖励并提供“去看看”入口；不做重复领奖摩擦。
- 若阶段奖励尚未配置或不可用，不展示空的锁定预告；可暂时只显示成长规则与阶段称号，避免承诺未兑现的奖励。
- 关系点仍按伙伴分别保存。更换伙伴不会清空进度，也不应制造失去奖励的压力。

#### 共同回忆区

- 将列表定义为“共同旅程”时间线，并在标题下简短说明：这里保存第一次、阶段变化和特别的共同成就。
- 优先保留有纪念意义的事件：首次共同练习、共同练习第 10 次等里程碑、关系阶段升级、首次搭配保存/套装完成（后两者待外观事件接入）。普通练习可汇总成“本周一起复习 4 次”，不逐条复制相同句子。
- 每条回忆包含日期、清晰事件标题、简短伙伴回应和对应角色插画/小图标。打开后可查看完整的安全摘要；不记录或展示用户的答案、记忆集标题、宫殿照片或原始学习内容。
- 顶部只保留一个“最新回忆”预览；时间线完整显示按时间排序的事件，避免顶部卡片和列表重复同一条练习。
- 新回忆只在真实事件发生时出现一次轻量提示。伙伴空间入口出现未读标记或“新回忆”数量；用户打开回忆后清除标记。不要因普通练习产生系统推送。
- 空态展示一条清楚的第一步提示，如“完成第一次练习后，这里会留下你们的第一段共同回忆”，并提供进入复习的轻入口。

### 回看率设计（不用签到压力）

- **即时回看**：阶段达成或重要里程碑发生时，练习完成反馈包含“查看这段回忆”；点开直达对应时间线事件。
- **可发现性**：伙伴空间的“共同旅程”标题展示未读新回忆数；进入时间线即标为已读。只对重要里程碑显示标记。
- **有积累感**：按月份/阶段组织时间线，展示“我们一起完成了 X 次练习”之类的周期总结；用户打开页面时能看到新旧变化。
- **柔性召回**：允许用户自愿开启每周伙伴回顾；默认关闭或按现有通知偏好执行，只在有新里程碑/周总结时发送，不因连续未登录而催促。
- **连接价值**：回忆卡可提供“再和伙伴复习一次”的次要入口，但不让用户为了读回忆必须开始练习，也不把回忆阅读计入学习成就。

### 后台可配置与服务端职责

- 管理端可配置阶段顺序/门槛、每阶段奖励类型和奖励引用、阶段名称与中英文说明、达成反馈文案；需要校验门槛递增、奖励有效且兼容对应伙伴。
- 管理端可配置哪些事件类型生成共同回忆、是否加入周期汇总以及中英文摘要模板；配置撤回时，历史用户事件应保持可读，不能因下架素材而变空白。
- 点数增量、事件去重、阶段判定、奖励解锁和已读状态由 API/服务端负责；客户端不能自行发放点数或解锁奖励。
- 复用现有 `CompanionBond` 与 `CompanionMemory`，只在确实需要时扩充奖励领取/解锁及阅读状态模型。若增加模型，更新 DTO、API 客户端类型、迁移、单元与集成测试；列表改为游标分页或按需加载，不能永久限制为最近 10 条。
- 记忆事件只保存允许展示的事件类型、时间、伙伴标识、去重来源和安全摘要，不复制学习集中的私人文本。

### 执行阶段

**阶段 1：让现有关系进度可理解（小版本）**

1. 移动端先补关系规则说明、当前点数/阶段门槛和准确的阶段文案；奖励暂未配置时不显示假奖励。
2. 统一练习完成后的点数反馈，让用户知道成长来自真实练习；每日问候反馈明确其为可选互动。
3. 调整回忆区空态、标题和最新事件展示，去掉重复的最新练习卡/列表记录。
4. 验收：新用户能在 5 秒内回答“关系如何成长”和“回忆何时出现”；点数展示与服务端值一致；未配置奖励不出现虚假解锁承诺。

**阶段 2：让阶段成长有实际回报**

1. 先选一位伙伴，为三个阶段各配置一个低成本但可感知的奖励（差异化回应/动作或场景装饰优先；外观物品其次）。
2. 管理端增加阶段与奖励配置界面、预览、启用/撤回校验；API 服务端按配置授予奖励并保证幂等。
3. 阶段升级时展示一次庆祝与奖励预览，并在伙伴空间提供回看入口；不弹出阻塞练习的弹窗。
4. 验收：门槛边界、重复提交、切换伙伴、奖励撤回、低等级用户、弱网重试均有测试；同一奖励不会重复发放，历史阶段不会倒退。

**阶段 3：把事件流做成可回看的共同旅程**

1. 定义并实现事件白名单、里程碑汇总和安全摘要；普通练习按日/周聚合，重要事件单独成条。
2. 增加时间线分页、按月分组、未读状态与一键定位到新回忆；加入首次练习、阶段升级、十次练习和外观里程碑。
3. 增加可选的每周回顾入口（先做应用内，不默认发推送）；通过小范围可用性测试确认回忆内容确实值得打开。
4. 验收：事件稳定去重、旧记录分页完整、已读状态跨设备一致、账号切换隔离；没有私人记忆内容进入回忆摘要。

### 指标与实验

- **核心回看指标**：新回忆产生后 7 天内打开该回忆/时间线的用户比例；另看每周伙伴空间回访用户比例和时间线二次打开率。
- **价值指标**：阶段奖励预览点击率、达成奖励后的衣橱/伙伴互动使用率、共同练习完成率。若回看增加但练习率下降，需检查是否把用户引向纯收集而非学习陪伴。
- **质量护栏**：推送关闭率、伙伴入口隐藏/退出率、练习中断率、同一事件重复率、回忆列表空白/加载失败率。
- 先记录基线，再小范围灰度阶段奖励预告和新回忆标记；每次只验证一个变化。不要把通知点击率或页面停留时长作为单独成功标准。

### 暂不做

- 不加衰减、饥饿、生病、连续登录惩罚、错过回忆消失或限时奖励。
- 不为每次练习都制造一条相同文案，不强制推送召回，也不要求用户手动领取每个成长奖励。
- 不在尚未有奖励内容时继续强调空洞的关系进度条。
